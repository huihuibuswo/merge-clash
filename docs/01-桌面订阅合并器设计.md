# 桌面订阅合并器设计文档

## 1. 文档信息

- 产品暂定名：Merge Clash
- 技术栈：Vue 3 + TypeScript + Naive UI + Tauri 2 + Rust + SQLite
- 目标平台：Windows 优先，架构兼容 macOS/Linux
- 配置格式：Mihomo/Clash YAML
- 参考实现：`D:\project\clash\clash.py`
- 模板参考：[andyxu12341/proxy-group-notes](https://github.com/andyxu12341/proxy-group-notes)，MIT License，分析版本 `a963ab2b89559c93e67b0088e3b1a70f903f6c40`
- 文档状态：MVP 设计稿
- UI 实现参考：[`docs/02-UI界面实现参考.md`](./02-UI界面实现参考.md)
- 设计系统：[`design-system/merge-clash/MASTER.md`](../design-system/merge-clash/MASTER.md)

## 2. 产品目标

开发一个本地桌面应用，完成以下闭环：

1. 管理多个订阅链接。
2. 拉取并解析各订阅中的 Clash/Mihomo 配置。
3. 选择一个目标客户端模板，由模板提供完整配置骨架，再将多个订阅中的节点合并进去。
4. 通过表单和拖拽/多选方式编辑最终代理组，不要求用户直接修改 YAML。
5. 预览、校验并生成最终 YAML 文件。
6. 在电脑局域网地址上发布订阅 URL，使同一局域网内的手机可以更新配置。

完成标准：用户可以只通过桌面界面完成“选择模板 -> 添加并测试订阅 -> 拉取 -> 合并 -> 编辑分组 -> 校验 -> 发布 -> 手机更新”的完整流程；发布内容与本地预览内容一致，应用重启后数据仍然存在。

## 3. 范围控制

### 3.1 Must：MVP 必须实现

- 订阅源新增、编辑、启用/停用、删除和手动刷新。
- 输入单个订阅链接时可以在保存前独立执行连通测试。
- 对订阅 URL 脱敏展示，不在日志中记录完整路径、查询参数或响应正文。
- 支持 Clash/Mihomo YAML 配置解析。
- 显示每个订阅的拉取状态、更新时间、节点数量和错误摘要。
- 提供版本化通用模板，并支持用户选择目标模板后进行合并。
- 首版内置 Mihomo 通用、Clash Verge Rev、FlClash 模板。
- 模板支持 `proxy-providers` 动态合并；需要桌面端统一清洗时支持静态节点展开。
- 节点合并与名称冲突处理。
- 代理组的可视化增删改、排序和成员选择。
- 规则引用校验与失效目标修复预览。
- 生成前校验、YAML 预览、导出文件。
- 启停局域网 HTTP 服务，展示可访问 URL、端口和当前局域网 IP。
- 为订阅地址生成不可预测的访问令牌。
- SQLite 持久化与数据库迁移。

### 3.2 Should：MVP 可一并实现

- 节点按来源、名称关键字、国家/地区文本进行筛选和批量加入分组。
- 内置“发达地区自动”“美国自动”“全部自动”等策略预设，并可预览匹配结果。
- 自动保存编辑草稿，发布版本单独确认。
- 生成二维码，方便手机录入订阅 URL。
- 保留最近若干次成功发布版本，支持回滚。
- 提供“使用当前已缓存数据合并”，用于部分订阅临时不可达的情况。

### 3.3 Defer：首版不实现

- 公网发布、内网穿透和云中转。
- 用户账号、多人协作、云同步。
- 自动识别机场地域语义并生成复杂分组。
- 通用 YAML 全字段可视化编辑器。
- 用户自定义模板、模板市场和在线模板下载。
- 规则集下载、规则生成器和策略脚本系统。
- 多配置项目并发发布；MVP 只维护一个活动项目，但数据结构保留项目 ID。
- 移动端管理后台。

## 4. 参考脚本行为与应保留的不变量

现有 `clash.py` 只作为节点合并、引用修复和原子写入的算法参考，不再继承任何订阅的顶层配置、代理组或规则。桌面版调整后的行为如下：

1. 用户先选择目标客户端模板，模板是最终配置的唯一骨架来源。
2. 按订阅优先级测试并解析节点；订阅自身的 DNS、TUN、规则和代理组默认不进入最终配置。
3. 静态模式的 `proxies` 按节点名称去重；动态模式生成 `proxy-providers` 并预检跨来源重名。
4. 使用模板定义的代理组和规则作为初始值，按来源插槽写入 provider `use` 或节点 `proxies`。
5. 清除模板实例中不存在的节点、组或内置策略引用。
6. 静态代理组清理后为空时，按模板的空组策略补入节点或 `DIRECT`。
7. 用户通过表单修改模板实例中的代理组，模板源文件保持只读。
8. 规则目标不存在时按模板声明的回退组修复，并生成可见修复记录。
9. 写文件和发布均采用不可变快照或原子替换，避免产生半个 YAML。

必须成立的不变量：

- 每个最终节点名称唯一。
- 每个代理组名称唯一。
- 每个草稿固定记录模板 ID 和模板版本，确保同一草稿可重复生成。
- 组不能直接引用自身。
- 代理组成员只能引用有效节点、有效组或 Mihomo 内置策略。
- 规则的策略目标必须有效；无法有效修复时阻止发布。
- 只有通过校验的快照可以成为“已发布版本”。
- 手机获取到的内容必须是最后一次成功发布版本，不能暴露编辑中的草稿。

```text

┌───────────────────────▼─────────────────────────────────┐
│ Tauri Commands                                         │
│ 参数校验、任务触发、状态查询、文件导出                 │
└───────────────┬───────────────────────┬─────────────────┘
                │                       │
┌───────────────▼──────────────┐  ┌─────▼─────────────────┐
│ Rust Domain Services         │  │ Local HTTP Publisher │
│ template / fetch / parse /   │  │ token 校验、快照读取 │
│ merge / validate / render    │  │ LAN 地址监听         │
└───────────────┬──────────────┘  └─────┬─────────────────┘
                │                       │
┌───────────────▼───────────────────────▼─────────────────┐
│ SQLite + App Data                                      │
│ 元数据、订阅缓存、编辑草稿、发布快照、设置             │
└─────────────────────────────────────────────────────────┘
```

### 5.1 前后端职责

前端负责：

- 页面展示、表单交互、筛选、排序和编辑草稿状态。
- 调用强类型 Tauri Command，不直接访问 SQLite。
- 展示后端返回的结构化校验问题，不自行判断最终配置是否合法。

Rust 负责：

- 加载内置模板、检查模板版本和目标客户端兼容能力。
- 网络请求、超时、响应大小限制和 YAML 解析。
- 合并算法、引用修复、配置校验和 YAML 序列化。
- SQLite 事务、版本快照和原子导出。
- 局域网 HTTP 服务生命周期、安全令牌和访问日志脱敏。

这一边界保证发布、文件和网络能力不受前端脚本任意控制，同时避免同一套合并规则在 TypeScript 和 Rust 中实现两遍。

## 6. 核心用户流程

### 6.1 首次使用

1. 用户选择目标客户端模板，例如 Clash Verge Rev 或 FlClash。
2. 用户输入单个订阅 URL，点击“测试连接”。
3. 应用显示 DNS/连接、HTTP、YAML 解析和节点识别结果；通过后用户保存订阅。
4. 用户继续添加其他订阅源，并设置名称和优先级。
5. 点击“拉取并合并”。
6. 后端拉取所有启用源进行解析；根据合并模式生成 provider 或展开节点，失败项独立展示。
7. 应用打开“分组编辑”页面，展示模板生成的代理组、合并节点和修复提示。
8. 用户调整代理组成员并执行校验。
9. 校验通过后点击“发布”。
10. 应用保存不可变快照并启动/刷新本地 HTTP 服务。
11. 用户在手机上扫描二维码或复制 URL，完成订阅更新。

### 6.2 后续更新

1. 用户保持原模板或明确切换模板，然后点击“刷新全部”。
2. 新数据只更新工作草稿，不覆盖已发布快照。
3. 应用展示新增、删除、重名和失效引用差异。
4. 用户确认分组变化并重新发布。
5. 手机继续使用同一个 URL，下一次更新时获取新快照。

## 7. 页面与交互设计

### 7.1 应用框架

- 左侧导航：概览、配置模板、订阅源、节点与分组、配置预览、本地发布、设置。
- 顶部状态区：草稿状态、最后发布时间、局域网服务状态。
- 全局任务区：显示当前拉取/合并进度，可取消尚未完成的拉取任务。

### 7.2 概览页

- 启用订阅数、最近成功拉取时间、节点总数、代理组数量。
- 当前草稿是否有未发布变更。
- 本地服务状态、访问地址和最近一次手机访问时间。
- 失败订阅与校验阻断问题。

### 7.3 配置模板页

模板卡片显示：模板名称、目标客户端、配置核心、模板版本、支持能力和简要默认行为。

首版内置：

| 模板 ID | 显示名称 | 目标与默认策略 |
|---|---|---|
| `mihomo-generic` | Mihomo 通用 | 面向标准 Mihomo 配置，采用保守 DNS、规则模式和通用代理组 |
| `clash-verge-rev` | Clash Verge Rev | 参考 proxy-group-notes，以 `proxy-providers + use` 动态合并，提供地区筛选组 |
| `flclash` | FlClash | 面向 FlClash 桌面/移动端，使用 Mihomo 兼容 provider 与策略组，避免依赖 Verge 扩展脚本 |

Clash Verge Rev 和 FlClash 通常都以 Mihomo 为核心，因此模板系统不应维护三套完全独立的合并代码。三者共享同一标准配置模型，只通过模板数据声明默认端口、DNS、TUN、sniffer、代理组、规则、合并模式、能力开关和兼容性约束。

参考仓库同时包含 Clash Verge 全局扩展 JavaScript。桌面应用不执行这类任意脚本，而是将其 `upsert group`、provider 注入、地区筛选和规则注入逻辑转成 Rust 内的声明式模板编译过程，保证可校验、可复现、可审计。

操作：选择模板、查看模板详情、选择合并模式、用当前订阅生成预览。切换模板或合并模式会重建草稿，并在确认框中说明现有分组编辑可能被替换；已发布版本不受影响。

合并模式说明：

- 动态合并：生成 `proxy-providers`，客户端自行刷新各原始订阅，适合长期维护。
- 静态合并：桌面端展开、清洗和去重节点后写入 `proxies`，适合精确编辑和稳定快照。

### 7.4 订阅源页

列表字段：

- 启用状态、名称、脱敏 URL、优先级。
- 最近状态、最近成功时间、延迟、节点数、错误摘要。

操作：新增、编辑、测试连接、刷新、调整优先级、删除。

订阅 URL 输入框默认按密码字段处理，保存后只显示域名和掩码；用户主动点击后才临时查看完整 URL。

新增/编辑弹窗必须提供独立的“测试连接”按钮。测试不要求先保存，也不改动现有快照。结果按阶段展示：

- URL 校验：仅接受 `http`/`https`，检查格式和重定向目标。
- 网络连接：DNS、TCP/TLS 和总耗时。
- HTTP 响应：最终状态码、响应大小、内容类型；不展示响应正文。
- 内容解析：YAML 是否可解析、顶层结构是否有效。
- 订阅识别：识别出的节点数量、节点类型摘要和兼容性警告。

测试通过不代表所有节点本身可用，它只证明订阅端点当前可访问且内容可以被应用解析。节点延迟/可用性检测属于另一项能力，不与链接连通测试混淆。

### 7.5 节点与分组页

采用左右布局：

- 左侧节点库：按来源、类型和文本过滤；支持多选。
- 中间代理组列表：显示组名、类型、成员数和校验状态，可排序。
- 右侧组编辑器：编辑组名、类型、成员、健康检查 URL、间隔、容差和 lazy。

组类型表单：

- `select`：只展示成员选择和排序。
- `url-test`：额外展示测试 URL、间隔、容差、lazy。
- `fallback`：额外展示测试 URL、间隔、lazy。
- `load-balance`：额外展示策略、测试 URL和间隔。

成员选择必须区分：节点、其他代理组、内置策略。禁止选择自身；若形成组引用环，在保存或校验时阻断并展示引用链。

地区自动组支持两种编辑视图：

- 简单模式：选择国家/地区标签和“排除通知节点”，应用生成过滤表达式。
- 高级模式：编辑 `filter` 与 `exclude-filter`，实时预览当前订阅快照中命中和被排除的节点。

参考仓库中的通知节点关键词（剩余、流量、套餐、到期、重置、官网、通知、更新等）作为内置排除预设维护，不硬编码到页面组件。

### 7.6 配置预览页

- 摘要视图：节点数、组数、规则数、来源失败数、自动修复数量。
- 变更视图：相对已发布版本的新增、删除、修改。
- YAML 只读预览与搜索。
- 校验问题按“阻断 / 警告 / 信息”分级，并关联到具体节点、组或规则。
- 操作：重新校验、导出 YAML、发布当前版本。

MVP 不提供任意 YAML 双向编辑，避免表单状态与文本状态冲突。高级用户可导出后自行处理。

### 7.7 本地发布页

- 服务开关、监听网卡、端口、令牌重置。
- 展示订阅 URL 和二维码。
- 展示 Windows 防火墙提示和连通性检查结果。
- 展示最近访问时间、来源 IP 和结果；日志中不显示令牌。
- 提供“从本机测试”和“复制手机检查步骤”。

## 8. 数据模型

SQLite 建议使用 `sqlx` 和 migration。MVP 核心表如下。

### 8.1 projects

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | UUID |
| name | TEXT | 项目名称 |
| template_id | TEXT | 当前内置模板 ID |
| template_version | INTEGER | 固定使用的模板版本 |
| merge_mode | TEXT | `proxy-providers` 或 `embedded-proxies` |
| created_at | INTEGER | Unix 毫秒时间戳 |
| updated_at | INTEGER | Unix 毫秒时间戳 |

内置模板以只读资源随应用发布，不保存为用户可编辑数据库记录。草稿和发布版本必须记录模板 ID 与版本；应用升级模板时不自动改写已有草稿或已发布版本。

### 8.2 subscriptions

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | UUID |
| project_id | TEXT | 所属项目 |
| name | TEXT | 用户可识别名称 |
| url | TEXT | 完整订阅 URL；日志和 UI 必须脱敏 |
| enabled | INTEGER | 0/1 |
| priority | INTEGER | 越小优先级越高 |
| last_test_status | TEXT | success/error/never |
| last_tested_at | INTEGER NULL | 最近独立连通测试时间 |
| last_status | TEXT | success/error/never |
| last_error | TEXT NULL | 脱敏错误摘要 |
| last_fetched_at | INTEGER NULL | 最近尝试时间 |
| last_success_at | INTEGER NULL | 最近成功时间 |

测试未保存 URL 时只返回临时 `ConnectionTestResult`，不写入订阅表。已保存订阅执行测试时，可更新最后测试状态，但测试失败不得覆盖最近一次成功快照。

### 8.3 subscription_snapshots

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | UUID |
| subscription_id | TEXT | 来源订阅 |
| content_hash | TEXT | SHA-256 |
| yaml_content | TEXT | 最近成功的原始配置缓存 |
| proxy_count | INTEGER | 节点数量 |
| fetched_at | INTEGER | 拉取时间 |

MVP 每个订阅至少保留最近一次成功缓存；可定期清理更老快照。

### 8.4 drafts

| 字段 | 类型 | 说明 |
|---|---|---|
| project_id | TEXT PK | 一个项目一个活动草稿 |
| revision | INTEGER | 乐观并发版本号 |
| template_id | TEXT | 生成草稿使用的模板 ID |
| template_version | INTEGER | 生成草稿使用的模板版本 |
| merge_mode | TEXT | 本次生成的合并模式 |
| config_json | TEXT | 规范化配置模型 |
| source_summary_json | TEXT | 本轮来源及错误摘要 |
| updated_at | INTEGER | 更新时间 |

编辑使用 JSON 结构存储，发布时再由 Rust 序列化为 YAML，避免把 YAML 文本当作数据库内的业务模型。

### 8.5 published_versions

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | UUID |
| project_id | TEXT | 所属项目 |
| version_no | INTEGER | 单调递增版本 |
| template_id | TEXT | 发布时使用的模板 ID |
| template_version | INTEGER | 发布时使用的模板版本 |
| merge_mode | TEXT | 发布时使用的合并模式 |
| yaml_content | TEXT | 不可变的发布内容 |
| content_hash | TEXT | SHA-256/ETag |
| validation_json | TEXT | 发布时校验摘要 |
| created_at | INTEGER | 发布时间 |

### 8.6 publish_settings

| 字段 | 类型 | 说明 |
|---|---|---|
| project_id | TEXT PK | 所属项目 |
| enabled | INTEGER | 是否自动启动服务 |
| bind_address | TEXT | 默认 `0.0.0.0`，UI 显示具体 LAN IP |
| port | INTEGER | 默认建议 17890，可修改 |
| access_token | TEXT | 256 位随机令牌 |
| active_version_id | TEXT NULL | 当前发布版本 |

## 9. 合并引擎设计

### 9.1 输入

- 启用订阅列表，按优先级稳定排序。
- 用户选择的模板 ID 与固定模板版本。
- 每个订阅本轮拉取结果或用户确认使用的最近成功缓存。
- 现有用户分组编辑草稿，可用于在刷新后迁移用户选择。

### 9.2 模板模型

模板由元数据和配置骨架组成，内置资源建议使用 YAML 表达，并在编译/启动测试中校验：

```yaml
id: flclash
version: 1
display-name: FlClash
core: mihomo
default-merge-mode: proxy-providers
supported-merge-modes: [proxy-providers, embedded-proxies]
capabilities:
  tun: true
  sniffer: true
  proxy-providers: true
provider-defaults:
  interval: 86400
  path-prefix: ./providers
  health-check:
    enable: true
    url: https://www.gstatic.com/generate_204
    interval: 300
match-presets:
  - id: developed-regions
    display-name: 发达地区自动
    include-tags: [TW, SG, JP, KR, US, CA, UK, AU, NZ, EU]
    exclude-preset: notice-and-non-target
  - id: united-states
    display-name: 美国自动
    include-tags: [US]
    exclude-preset: notice-nodes
source-slots:
  - group: 节点选择
    mode: all
  - group: 发达地区自动
    mode: preset
    preset: developed-regions
fallback-group: 节点选择
config:
  mixed-port: 7890
  allow-lan: true
  mode: rule
  proxies: []
  proxy-groups:
    - name: 节点选择
      type: select
      proxies: [发达地区自动, 美国自动, DIRECT]
    - name: 发达地区自动
      type: url-test
      url: https://www.gstatic.com/generate_204
      interval: 300
      tolerance: 50
      lazy: true
  rules:
    - MATCH,节点选择
```

模板规则：

- `config` 提供完整最终配置骨架，订阅不得覆盖其顶层字段。
- `supported-merge-modes` 声明模板是否支持动态 provider 或静态节点展开。
- `provider-defaults` 参考 proxy-group-notes，为每个订阅生成稳定 provider 名称、独立缓存路径和健康检查。
- `source-slots` 声明订阅来源应注入哪些组；动态模式生成 `use`，静态模式生成 `proxies`。
- `match-presets` 用结构化地区标签和排除预设生成 `filter`/`exclude-filter`，避免在多个模板复制超长正则。
- `fallback-group` 用于修复无效规则目标。
- `capabilities` 控制 UI 可编辑项和兼容性校验。
- 模板 ID 不变，内容变化必须递增版本。
- 模板必须通过自身校验：组名唯一、插槽存在、回退组存在、预设存在、规则目标有效。

### 9.3 参考仓库的采纳范围

直接采纳的设计思想：

- Mihomo 多订阅使用 `proxy-providers`，代理组通过 `use` 引用全部来源。
- 主入口采用 `select`，可选择地区自动组、单个 provider 节点和 `DIRECT`。
- 自动策略组使用 `url-test`、健康检查 URL、`interval`、`tolerance`、`lazy` 和 `expected-status`。
- 使用 `filter`/`exclude-filter` 按节点名称形成“发达地区自动”“美国自动”等策略。
- 排除流量、套餐、到期、通知、客户端更新等伪节点。
- 规则最终统一指向模板声明的主选择组。

不直接采纳的部分：

- 不执行 Clash Verge 全局扩展 JavaScript；对应行为由 Rust 模板编译器实现。
- 不把两个 provider 写死为 `sub_a`、`sub_b`；根据订阅 UUID 生成稳定且合法的 provider ID，支持任意数量订阅。
- 不把特定业务域名（例如参考模板中的 Homestyler）放入通用模板；仅作为可选规则预设。
- 不默认依赖单一 GitHub 规则地址而不提示；模板详情必须展示所有外部 rule-provider 地址和离线影响。
- 不原样复制超长地区正则到每个模板；使用共享预设生成，并为来源代码保留 MIT 版权与许可证说明。

### 9.4 单链接连通测试与正式拉取

连通测试与正式拉取共用同一个安全 HTTP 客户端和解析器，避免出现“测试成功但刷新采用另一套规则”的偏差。

建议返回结构：

```rust
struct ConnectionTestResult {
    reachable: bool,
    stage: TestStage,
    http_status: Option<u16>,
    elapsed_ms: u64,
    response_bytes: Option<u64>,
    proxy_count: Option<usize>,
    proxy_types: Vec<String>,
    warnings: Vec<ValidationIssue>,
    error: Option<SafeError>,
}
```

测试发起 `GET` 而不是只发 `HEAD`，因为许多订阅服务不支持 HEAD，且必须读取受限大小的正文才能验证 YAML 和节点。测试结果只用于即时反馈，不自动加入合并，也不把完整响应写入日志。

### 9.5 拉取约束

- 仅允许 `http` 和 `https` URL；默认推荐 `https`。
- 单请求连接与总超时，默认总超时 30 秒。
- 限制重定向次数，重定向后仍需校验协议。
- 限制响应体大小，例如 20 MiB，防止异常订阅耗尽内存。
- 设置明确 User-Agent。
- 各订阅失败互不影响；全部失败且无获准缓存时，本轮合并失败。
- 错误信息不得包含完整 URL、Authorization、Cookie 或响应正文。

### 9.6 解析与规范化

解析后必须确认顶层为对象，且 `proxies` 是可识别列表。订阅的其他字段可用于诊断但默认不进入最终配置；未知节点字段原样保留，以提高 Mihomo 协议兼容性。

内部模型至少包含：

```rust
struct NormalizedConfig {
    template_id: String,
    template_version: u32,
    merge_mode: MergeMode,
    template_config: serde_yaml::Mapping,
    proxy_providers: Vec<ProxyProvider>,
    proxies: Vec<ProxyNode>,
    proxy_groups: Vec<ProxyGroup>,
    rules: Vec<String>,
}
```

节点和代理组中的未知字段可使用 `serde_yaml::Value` 保留，避免序列化时丢失供应商扩展字段。

### 9.7 节点冲突策略

静态 `embedded-proxies` 模式与参考脚本一致：按名称去重，优先级较高的订阅获胜，并生成冲突报告。

冲突报告包含：节点名、获胜来源、被忽略来源，不展示节点凭据。后续可增加“自动添加来源后缀”，但首版不自动改名，因为改名会影响原有代理组引用和用户认知。

动态 `proxy-providers` 模式下，节点最终由 Mihomo 从多个 provider 装载，桌面应用无法在客户端装载阶段可靠去重。应用仍用测试快照预检同名节点；检测到跨 provider 重名时默认阻断发布，用户可切换静态模式。只有目标核心经过兼容测试并由模板明确声明支持安全重命名时，才允许模板采用 provider 级前缀方案。

### 9.8 代理组处理

自动合并阶段：

1. 深拷贝所选模板的代理组作为初始值。
2. 按模板 `source-slots` 注入来源：动态模式写入 provider `use`，静态模式写入节点 `proxies`。
3. 对地区策略预设生成 `filter` 和 `exclude-filter`，并用当前订阅快照展示命中预览。
4. 清理失效成员、自引用和重复成员。
5. 对模板声明的必需组和字段进行校验，不临时创造模板之外的结构。
6. 静态组为空时执行模板的空组策略，例如补入全部节点或 `DIRECT`。
7. 记录模板实例化过程中的注入、清理和回退结果。

可视化编辑阶段：

- 用户可以覆盖上述自动结果。
- 每次保存后执行局部校验；发布前执行全量校验。
- 刷新订阅后，通过稳定标识 `(来源订阅 ID, 节点名)` 尽量保留组成员关系。
- 消失节点从组中移除并形成警告；不静默替换为其他节点。
- 动态模式保存的是 provider 选择和筛选条件，节点列表只作为预览；静态模式保存精确节点成员。

### 9.9 规则处理

MVP 使用模板规则，不合并订阅内携带的规则。处理方式：

- 有效目标：节点名、代理组名、Mihomo 内置策略。
- 支持 `no-resolve` 等规则后缀，正确定位策略字段。
- 失效目标替换为模板声明的 `fallback-group`，并在发布前列出修复记录。
- 补充本地网段直连规则时保证幂等。
- 无法解析的非空规则保留但产生警告；明确错误且可能导致配置不可加载时阻断发布。

### 9.10 校验层级

阻断发布：

- YAML 无法序列化或顶层结构错误。
- 模板不存在、模板版本不可用或模板自身校验失败。
- 节点/代理组重名。
- 代理组引用不存在目标、直接自引用或循环引用。
- 必需字段缺失、代理组类型不受支持。
- 规则策略目标无效且无法修复。
- 没有可发布快照。

警告：

- 部分订阅拉取失败。
- 使用了缓存而非实时数据。
- 节点名称冲突并发生丢弃。
- 未知 Mihomo 字段或未完全识别的规则格式。
- 当前主选择组成员为空但已补入 `DIRECT`。

## 10. 局域网订阅服务

### 10.1 HTTP 接口

MVP 只暴露一个只读接口：

```http
GET /subscription/{token}/config.yaml
```

成功响应：

```http
HTTP/1.1 200 OK
Content-Type: text/yaml; charset=utf-8
Cache-Control: no-cache
ETag: "<content_hash>"
Content-Disposition: inline; filename="merge-clash.yaml"
```

可支持 `If-None-Match` 并返回 `304 Not Modified`。无效令牌统一返回 `404`，避免暴露服务中是否存在某个项目。

动态模式发布的 YAML 含原始订阅 URL 和 `proxy-providers`，手机取得配置后由 Mihomo 直接刷新 provider；本地订阅 URL 用于更新模板、分组和规则。静态模式发布的 YAML 不含原始订阅 URL，但包含展开后的节点凭据；手机必须再次访问本地 URL 才能取得新节点。两种模式都属于敏感配置。

### 10.2 监听方式

- 默认只在用户打开“局域网发布”后监听。
- 监听 `0.0.0.0:<port>`，界面枚举并展示可用私有 IPv4 地址，例如 `http://192.168.1.20:17890/...`。
- 不把 `127.0.0.1` 地址提供给手机。
- 网卡/IP 变化后自动刷新展示地址，令牌和端口保持不变。
- 端口冲突时不自动随机切换，提示用户选择新端口，避免手机保存的 URL 静默失效。

### 10.3 安全边界

局域网并非可信环境。MVP 至少需要：

- 使用加密安全随机数生成 32 字节令牌，并用 URL-safe Base64 或十六进制编码。
- 日志、通知和错误报告中永不记录完整订阅 URL 或令牌。
- HTTP 服务只提供已发布快照，不访问任意文件，不接受路径参数和写操作。
- 固定响应头并阻止目录遍历。
- 增加基础速率限制和并发连接上限，防止局域网误请求耗尽资源。
- 提供一键重置令牌；重置后旧 URL 立即失效。
- 应用退出或用户关闭发布时停止监听。
- 明确提示 Windows 防火墙可能需要允许“专用网络”访问，不建议允许公用网络。

MVP 局域网传输是 HTTP，连接同一 Wi-Fi 的其他设备理论上可观察明文流量。令牌主要防止偶然访问，不能替代 TLS。若配置中包含敏感节点凭据，用户应只在可信专用局域网开启服务。局域网 HTTPS 因证书信任和手机兼容成本延后评估。

### 10.4 服务生命周期

- Tauri 启动时读取设置；仅当用户已启用且存在有效发布版本时启动服务。
- 发布新版本通过原子替换活动版本 ID 生效，正在进行的请求继续返回一致快照。
- HTTP handler 每次读取活动版本的不可变内容或内存中的原子快照。
- 服务启动失败不影响桌面编辑功能，但必须在全局状态区明确显示失败。

## 14. 一致性、失败与恢复

### 14.1 草稿与发布隔离

- 合并结果先写入草稿事务。
- 用户编辑只修改草稿，并通过 `revision` 防止旧页面覆盖新修改。
- 发布事务中重新校验草稿、生成 YAML、写入发布版本并更新活动版本。
- 任一步骤失败时，旧活动版本保持不变。

### 14.2 部分订阅失败

- 默认：成功源参与合并，失败源显示警告。
- 若失败源存在最近成功缓存，必须由设置或当次确认决定是否使用，不能静默混用新旧数据。
- 全部实时拉取失败时，不自动覆盖现有草稿或发布版本。

### 14.3 应用异常退出

- SQLite 开启外键并使用事务。
- 发布版本不可变，活动版本切换是单条事务更新。
- 文件导出使用同目录临时文件加原子替换。
- HTTP 服务始终读取已提交快照，不读取临时文件。

## 15. 隐私与安全

- 订阅 URL、节点密码、UUID、密钥、令牌都视为敏感数据。
- 默认不采集遥测，不上传订阅或生成配置。
- UI 日志只展示脱敏 URL；导出诊断包前再次清洗。
- SQLite 文件本身默认不加密，因此不宣称“加密存储”。首版至少依赖操作系统用户目录权限，并在文档中说明风险。
- 若后续需要强保护，优先评估系统凭据库保存订阅 URL/令牌，或 SQLCipher；这不是 MVP 阻断项。
- SSRF 风险：桌面用户可以添加 URL，但应用仍应限制协议并阻止访问非 HTTP(S) scheme。是否禁止本机/内网目标需要产品权衡，因为本应用本身可能需要访问局域网订阅源；首版允许但显示目标主机。
- Tauri capability 只开放需要的命令、对话框和事件能力，不给前端通用 shell 权限。
- 动态 provider 模式会把原始订阅 URL 写入发布 YAML，启用前必须在界面明确提示；诊断、二维码和访问日志仍不得额外泄露这些地址。

## 16. 可观测性

结构化任务日志至少包含：任务 ID、订阅 ID、阶段、耗时、结果类型和脱敏错误码。

不记录：完整订阅 URL、完整 YAML、节点凭据、发布令牌。

用户可见错误应区分：

- 网络连接/超时/证书错误。
- HTTP 状态错误。
- YAML 解析错误。
- Clash/Mihomo 结构不兼容。
- 合并或校验错误。
- SQLite/磁盘错误。
- 端口占用/防火墙/网卡不可用。

## 17. 测试与验收

### 17.1 Rust 单元测试

- 三个内置模板均能通过模板自身校验并稳定生成 YAML。
- 模板节点插槽、回退组、能力约束和版本固定行为。
- 地区标签生成稳定的 `filter`，通知节点预设生成稳定的 `exclude-filter`。
- provider ID、缓存路径对任意订阅数量保持唯一、稳定且不包含用户密钥。
- 节点按名称去重与优先级获胜。
- 空项、非对象节点和缺失名称被正确忽略或报告。
- 代理组失效引用、自引用、重复引用清理。
- 代理组循环引用检测。
- 按模板实例化代理组、节点插槽注入和空组回退行为。
- 带 `no-resolve` 规则的策略字段识别。
- 失效规则目标修复与局域网规则幂等插入。
- YAML 未知字段往返保留。
- 发布令牌生成和常量时间比较策略。

### 17.2 集成测试

- 未保存 URL 的单链接测试：成功、DNS 失败、TLS 失败、HTTP 错误、超时、重定向、超大响应、非法 YAML 和无节点内容。
- 模拟多个 HTTP 订阅：成功、超时、重定向、超大响应、非法 YAML、部分失败。
- 对同一 URL，连通测试与正式刷新使用一致的协议限制、超时、大小限制和解析规则。
- 分别使用 Mihomo 通用、Clash Verge Rev、FlClash 模板生成配置，并验证订阅顶层字段不会覆盖模板。
- 动态模式生成与订阅数量一致的 `proxy-providers`，所有来源组的 `use` 引用完整且无悬空项。
- 静态模式不生成 `proxy-providers`，节点去重后写入 `proxies`，输出不包含原始订阅 URL。
- 动态模式发现跨 provider 同名节点时按设计阻断或执行模板明确支持的兼容策略。
- SQLite migration、草稿保存、revision 冲突、发布事务和版本回滚。
- 本地 HTTP 服务：正确令牌 200、错误令牌 404、ETag 304、服务停止后不可访问。
- 发布失败时旧版本保持可访问。

### 17.3 前端测试

- 订阅表单脱敏与错误展示。
- 未保存 URL 可以执行测试，分阶段展示结果，失败不会写入订阅或覆盖缓存。
- 模板选择、详情展示和切换模板二次确认。
- 组类型切换时字段显示正确。
- 节点筛选、多选、成员排序和自引用禁用。
- 校验阻断时发布按钮不可执行。
- 草稿未发布提示和服务状态展示。

### 17.4 手动验收场景

1. 在未保存订阅弹窗中分别测试一个有效链接和一个无效链接，结果明确且不泄露完整 URL。
2. 依次选择 Mihomo 通用、Clash Verge Rev 和 FlClash 模板，对相同订阅生成配置，确认模板默认字段与分组符合各自定义。
3. 分别选择动态和静态合并：动态 YAML 包含 provider 与 `use`，静态 YAML 包含展开节点且不含原始订阅 URL。
4. 确认订阅中的 DNS、规则和代理组不会覆盖所选模板，只提取节点或生成 provider。
5. 添加至少三个真实订阅，其中一个不可用，仍能得到明确的部分成功结果。
6. 制造同名节点，确认静态模式获胜来源符合优先级，动态模式给出阻断提示。
7. 在表单中调整地区标签、通知节点排除预设和 `url-test` 参数，命中预览与生成 YAML 一致。
8. 在表单中创建 `select` 和 `url-test` 组并调整成员顺序。
9. 删除被组引用的节点，确认出现失效提示且不能生成错误发布版本。
10. 发布后用电脑浏览器访问订阅 URL，内容与预览哈希一致。
11. 手机与电脑连接同一专用局域网，可通过同一 URL 更新。
12. 修改草稿但不发布，手机仍获取旧版本。
13. 重新发布后 URL 不变、内容更新、ETag 改变。
14. 重置令牌后旧 URL 返回 404，新 URL 可用。
15. 端口被占用、网络切换和应用重启时均有明确状态，不丢失已发布数据。

## 18. 对抗式审查结论

### 18.1 Launch blockers

- 不能把编辑中的草稿直接提供给手机，否则半成品或校验失败配置会被客户端拉取。
- 不能使用无令牌的固定局域网 URL，否则同网段任何设备都可直接取得包含节点凭据的配置。
- 不能记录完整订阅 URL、响应正文或生成 YAML；这些内容通常含长期凭据。
- 不能让订阅内容覆盖模板的顶层网络、DNS、TUN、规则或发布设置，否则模板选择失去确定性且可能引入危险配置。
- 单链接测试和正式拉取不能使用两套不同的网络/解析实现，否则测试结果不可信。
- 动态模式不能忽略 provider 间同名节点冲突；这可能让代理组选择结果依赖客户端实现。
- 模板引用远程 rule-provider 时必须可见、可关闭且有失败提示，不能把第三方 GitHub 可用性当作隐含前提。
- 发布必须事务化，失败时继续提供上一成功版本。
- 必须检测代理组循环引用；参考脚本只排除了直接自引用，桌面编辑器允许任意组关系后风险更高。
- 必须限制响应大小、超时和重定向，避免恶意或异常订阅耗尽应用资源。

### 18.2 Follow-up

- SQLite/本地敏感字段加密。
- 局域网 HTTPS 或一次性配对机制。
- 更完整的 Mihomo schema 校验和真实内核兼容测试。
- 自动定时拉取与系统托盘后台服务。
- 多项目、多发布端点和跨设备管理。

## 20. 待确认但不阻塞 MVP 的产品决策

- 三个首发模板的具体默认 DNS、TUN、sniffer 和规则内容，需要结合真实客户端导入测试后冻结为模板 v1。
- 节点同名冲突是否长期维持“高优先级覆盖”，还是允许用户选择自动重命名。
- 首版是否允许使用订阅最近成功缓存参与合并，建议默认不静默使用、由用户确认。
- 应用关闭后局域网服务是否继续运行。基于 Tauri 单进程模型，MVP 建议应用退出即停止；需要后台常驻时使用系统托盘而非独立服务。
- 是否需要定时自动刷新。建议首版先手动刷新，稳定后再增加调度。

以上决策不会改变核心架构，可在原型验收后确定。
